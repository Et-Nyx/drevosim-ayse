# SSD cache subvolume (`/mnt/ssd/cache`) — Operator's Manual

A practical guide to the fast-scratch subvolume on the NVMe SSD, and how
to make new services consume it. Read this when you need large, fast
temporary storage for a service, and when you're wondering whether
something belongs on the SSD, the HDD, or the tmpfs root.

The mount lives at **`/mnt/ssd/cache`** on `ayse` and is backed by the
`@cache` btrfs subvolume on the same NVMe SSD that holds `/nix`.

## What it is and what it isn't

| This is | This is not |
|---------|-------------|
| A btrfs subvolume (`@cache`) on the NVMe SSD, mounted at `/mnt/ssd/cache` | A separate disk — it lives on the same partition as `/nix` (the NVMe SSD) |
| ~180 GB of fast scratch space (the SSD has 222 GB total, `/nix` uses ~26 GB) | A backup of `/nix`. The two subvolumes are independent. |
| Persistent across reboots (it's on the SSD, not on tmpfs) | Preserved via the `preservation` module. The SSD is already persistent — no `preservation.preserveAt` entry is needed. |
| Where services put **fast, throwaway-but-too-big-for-tmpfs** state (rclone VFS cache, browser cache, game scratch) | Where you put **durable personal state**. That still goes on the HDD under `/persistent` via `preservation`. |
| Mounted at boot by `disko`, declared in `mon/mehmangi/ayse/nukleus/disko.nix` | Created at runtime. The subvolume is declared declaratively and mounted by systemd-fstab-generator. |

## How it works

```
┌──────────────────────────────────────────────────────────────────────┐
│  /dev/nvme0n1p3  (NVMe SSD, Btrfs)                                  │
│                                                                      │
│  ├─ @nix          (subvol=256)  → mounted at /nix                   │
│  │   └─ 26 GB used by the Nix store, system profiles, boot loader   │
│  │                                                                   │
│  └─ @cache        (subvol=258)  → mounted at /mnt/ssd/cache        │
│      └─ ~180 GB free, used by rclone-ps4, firefox, etc.            │
│                                                                      │
│  Mount unit: mnt-ssd-cache.mount  (generated by systemd-fstab-      │
│  generator from the fstab entry disko creates)                      │
└──────────────────────────────────────────────────────────────────────┘
```

The disko config (`mon/mehmangi/ayse/nukleus/disko.nix`) declares the
`/@cache` subvolume alongside `@nix`:

```nix
subvolumes = {
  "/nix" = {
    mountOptions = [ "subvol=nix" "noatime" ];
    mountpoint = "/nix";
  };
  "/@cache" = {
    mountOptions = [
      "subvol=@cache"
      "noatime"
      "compress=zstd"
    ];
    mountpoint = "/mnt/ssd/cache";
  };
};
```

On every `nixos-rebuild switch`, disko sees the existing subvolume and
just mounts it. The subvolume was created manually once with:

```bash
sudo mount -o subvolid=5 /dev/nvme0n1p3 /tmp/btrfs-top
sudo btrfs subvolume create /tmp/btrfs-top/@cache
sudo umount /tmp/btrfs-top
```

The `@` prefix is the btrfs convention for top-level subvolumes. Note
that `@nix` and `@cache` were created differently historically
(`@nix` was created as `nix` without the `@`, `@cache` with it), so
their mount options differ: `subvol=nix` vs `subvol=@cache`. This is
cosmetic and both mount correctly.

## The ephemeral-system triangle: tmpfs vs SSD vs HDD

ayse is an impermanent system. Every byte of storage belongs to one of
three tiers, and knowing which tier to use for what is the central
design question:

| Tier | Mount point | Speed | Persistence | Capacity | Use for |
|------|-------------|-------|-------------|----------|---------|
| **tmpfs (root)** | `/` | ~5 GB/s (RAM) | None — wiped on reboot | 4 GB (25% of 16 GB RAM) | The OS itself, running processes, small transient state, `/tmp`, `/var/log`, `/var/cache` (when small) |
| **SSD subvolume** | `/mnt/ssd/cache` | ~1–2 GB/s (NVMe) | Persistent (btrfs SSD) | ~180 GB free | Fast scratch: large write buffers, browser cache, game installs, build caches — anything too big for tmpfs and too hot for HDD |
| **HDD** | `/persistent` | ~100–200 MB/s (spinning) | Persistent (btrfs HDD) | ~830 GB free | Durable personal state: SSH keys, `/home/eter`, KDE config, games you want to keep, etc. The `preservation` module manages the copy. |

**The decision tree:**

1. Does it need to survive a reboot? **Yes** → SSD or HDD (not tmpfs).
2. Is it accessed frequently (every few seconds)? **Yes** → SSD.
3. Is it large (>100 MB) and frequently accessed? **Yes** → SSD.
4. Otherwise → tmpfs if it fits, or HDD if it needs to survive.

Examples:

- A 3 GB `.pkg` mid-transfer: **SSD** (tmpfs is too small, HDD is too slow for the active transfer).
- A 200 MB Firefox profile: **SSD** (frequently accessed, survives reboot).
- A 50 MB fish shell history: **HDD** (via `preservation.eter`).
- `/tmp` scratch for a one-off compile: **tmpfs** (ephemeral, fast).
- A 50 GB Steam game: **HDD** (large, infrequently accessed after install; or SSD if you want fast load times and have space).

## Adding a new consumer

The pattern: each service gets its own subdirectory under
`/mnt/ssd/cache/<service-name>/`, with ownership set by a tmpfiles
rule. The service is then told to depend on the mount via `Requires=`
and `After=` in its systemd unit (or `requiresMountsFor` if it's a
mount unit itself).

### Step 1: Decide the path

Use `/mnt/ssd/cache/<service-name>/`. Examples:

- `/mnt/ssd/cache/rclone-ps4/` (existing)
- `/mnt/ssd/cache/firefox/profile/` (planned)
- `/mnt/ssd/cache/steam/` (planned, for game installs)

Pick a name that's clear and unique. Avoid versioning (no `v1`, `v2`).

### Step 2: Add a tmpfiles rule to your module

In your service module, add:

```nix
systemd.tmpfiles.rules = [
  "d /mnt/ssd/cache/<service-name> 0755 <user> <group> - -"
];
```

The directory is created at boot with the right ownership. The
`<user>:<group>` should match the user the service runs as. For
example, the rclone-ps4 service runs as root, so its tmpfiles rule is
`d /mnt/ssd/cache/rclone-ps4 0755 root root - -`.

The mount point `/mnt/ssd/cache` itself is created by disko, so you
don't need a tmpfiles rule for the parent.

### Step 3: Make your service wait for the mount

The mount unit is `mnt-ssd-cache.mount` (note: **literal dash, not
`\x2d`** — the `\x2d` escape is only for directive values, not the
unit name on disk). The actual generator file is at
`/run/systemd/generator/mnt-ssd-cache.mount`.

In your service:

```nix
systemd.services."<service-name>" = {
  description = "...";
  after = [
    "network-online.target"
    "mnt-ssd-cache.mount"   # literal dash
  ];
  wants = [ "network-online.target" ];
  requires = [ "mnt-ssd-cache.mount" ];
  wantedBy = [ "multi-user.target" ];
  # ...
};
```

If you only want soft ordering (the service can start before the mount
is ready and just retry), use `wants` instead of `requires`.

### Step 4: Point your service at the new path

For rclone: `--cache-dir=/mnt/ssd/cache/<service-name>/`

For Firefox: `programs.firefox.profiles.default.path = "/mnt/ssd/cache/firefox/profile";`

For a custom service: whatever config knob it exposes, set it to the
new path.

### Step 5: Migration (if you're moving existing state)

1. **Stop the service** so it doesn't write to the old path.
2. **Copy the old state** to the new path:
   ```bash
   sudo cp -a /old/path/ /mnt/ssd/cache/<service-name>/
   sudo chown -R <user>:<group> /mnt/ssd/cache/<service-name>/
   ```
3. **Update the module** to point at the new path.
4. **Rebuild and start** the service.
5. **Verify** the service works with the new path.
6. **Delete the old state** (only after confirming the new path works):
   ```bash
   sudo rm -rf /old/path/
   ```
7. If the old path was inside `~/.config` and you're moving it out,
   you may want to clean up the empty parent dir from `/persistent`
   on the next boot (preservation will sync the deletion).

### Step 6: Add a doc note in your module

Add a comment in your `*.nix` file explaining the cache location, and
add an entry to your `gida/<module>.md` guide under a "State and
persistence" section.

### Step 7: Update the README

Add a row to the "Who uses it today" table in this file. The README
also has a todo item for "audit other `~/.cache` consumers" — when you
add one, cross it off or expand it.

## Migration checklist

When moving a service from tmpfs/HDD to the SSD:

- [ ] Stop the service
- [ ] Copy old state to `/mnt/ssd/cache/<service>/` with correct ownership
- [ ] Update the module: tmpfiles rule, `--cache-dir` or equivalent, `after`/`requires` on `mnt-ssd-cache.mount`
- [ ] `nix flake check`
- [ ] `nixos-rebuild switch --flake .`
- [ ] Start the service
- [ ] Verify the service works (functional test, not just "active")
- [ ] Run a size check: `du -sh /mnt/ssd/cache/<service>/`
- [ ] Delete the old state (only after verification)
- [ ] Update the service's gida/ guide
- [ ] Update this file's "Who uses it today" table
- [ ] Commit

## Disaster recovery

### The SSD subvolume disappears

If `@cache` is missing (e.g., the SSD failed or was wiped):

1. Boot from a NixOS installer USB.
2. Mount the SSD partition at `/mnt`:
   ```bash
   mount /dev/nvme0n1p3 /mnt
   ```
3. Create the subvolume:
   ```bash
   btrfs subvolume create /mnt/@cache
   ```
4. Unmount and reboot:
   ```bash
   umount /mnt
   reboot
   ```
5. On reboot, disko will mount the empty `@cache` at `/mnt/ssd/cache`.
   Services that depend on it will start fresh (empty caches, etc.).

The disko config is idempotent: it will not reformat the SSD, it will
just see the existing subvolume and mount it. The `subvol=@cache` and
`/mnt/ssd/cache` mountpoint are declared in `disko.nix`, so a fresh
subvolume created by hand will be picked up automatically.

### The mount unit disappears

If `mnt-ssd-cache.mount` is not in `systemctl list-units --type=mount`:

- Check the generator: `ls /run/systemd/generator/mnt-ssd-cache.mount`
- If it's there, the unit is registered but systemd hasn't seen it:
  ```bash
  sudo systemctl daemon-reload
  sudo systemctl restart local-fs.target
  ```
- If it's not there, the fstab entry is missing. Check
  `cat /etc/fstab | grep ssd` and re-run `nixos-rebuild switch`.

### The mount is present but read-only

This shouldn't happen because we mount with default options. If it
does, check `mount | grep ssd` for the `ro` flag and remount:

```bash
sudo mount -o remount,rw /mnt/ssd/cache
```

## FAQ

### Why `@cache` and not `@scratch` or `@tmp`?

`@cache` is the established convention for "service caches" and
matches the pattern of `/var/cache/`. The directory is for caching
state that's faster to recreate than to read from HDD — that's the
essence of a cache.

### Why is the mount point `/mnt/ssd/cache` and not `/var/cache`?

`/var/cache` is on the tmpfs root. Putting the SSD subvolume there
would mean the tmpfs path is a mount, which interacts badly with
tmpfiles rules and the preservation module. `/mnt/ssd/cache` is a
dedicated mount, so the tmpfs root is untouched and the SSD subvolume
is a clean, well-defined filesystem mount.

### Why compress=zstd?

The cache contains large files (game installs, browser cache, .pkg
transfers). zstd compresses them at ~3:1 with minimal CPU cost. For
small random reads (which the browser cache does), the compression
overhead is negligible compared to the SSD read speed.

### What if I run out of space?

The SSD has ~180 GB free. The current consumers use:
- rclone-ps4: up to 10 GB (VFS cache cap)
- Firefox (planned): ~500 MB (profile + cache)
- Total current: ~10.5 GB

If you add a large consumer (e.g., Steam at 50 GB), you'll have plenty
of headroom. If you somehow fill it:

```bash
du -sh /mnt/ssd/cache/* | sort -h
```

will show who's using what. Old rclone cache entries are auto-evicted
by `--vfs-cache-max-age=24h`. Browser caches can be cleared from the
browser's preferences.

### Why doesn't this need a preservation rule?

The SSD is persistent storage. The btrfs subvolume on the SSD
survives reboots naturally. The `preservation` module is for syncing
state from tmpfs to HDD at shutdown — the SSD doesn't need that.
The contents of `/mnt/ssd/cache/` are persistent because the SSD is
persistent, full stop.

### Can I put secrets here?

No. The SSD is encrypted only at the device level (if at all — the
default install doesn't enable LUKS on `/dev/nvme0n1`). The HDD
(`/persistent`) is in the same boat. The `siri/` directory uses
agenix for encryption at rest. For secrets, use `siri/` and
`config.age.secrets.<name>.path`. The SSD cache is for non-secret
state: caches, buffers, scratch.

### Can I share the subvolume between services?

Each service gets its own subdirectory, but they all live on the
same btrfs subvolume. They can technically read each other's
directories, but the permissions prevent it. The tmpfiles rules set
ownership per service. Don't rely on isolation beyond Unix
permissions — a service running as root could read any directory.

### What if I want a separate subvolume per service?

You can declare more subvolumes in `disko.nix`:
```nix
subvolumes = {
  ...
  "/@firefox" = {
    mountOptions = [ "subvol=@firefox" "noatime" "compress=zstd" ];
    mountpoint = "/mnt/ssd/firefox";
  };
};
```

But that's more disko config for no real win (you'd need separate
mounts, and the per-service subdirectory inside one subvolume is
already isolated by permissions). One subvolume is enough for now.

## Quick reference

```bash
# Is the SSD subvolume mounted?
mount | grep ssd

# How much space is used and by whom?
du -sh /mnt/ssd/cache/* 2>/dev/null | sort -h

# Free space
df -h /mnt/ssd/cache

# Service mount unit
systemctl status mnt-ssd-cache.mount

# The actual generator file
cat /run/systemd/generator/mnt-ssd-cache.mount

# Speed test (write 500 MB to the SSD subvolume)
dd if=/dev/zero of=/mnt/ssd/cache/speedtest bs=1M count=500 oflag=direct status=none && rm /mnt/ssd/cache/speedtest

# Disko declaration
grep -A 5 '@cache' mon/mehmangi/ayse/nukleus/disko.nix
```

If a service can't start because the mount is "not found", check
that you're using `mnt-ssd-cache.mount` (literal dash), not
`mnt-ssd\x2dcache.mount` (escaped). The escape is only valid in
directive values, not unit names on disk.
